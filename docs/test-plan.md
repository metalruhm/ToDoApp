# テスト計画（バックエンド）

> ステータス: **初稿（AI作成・レビュー待ち）**
> 元資料: [api-spec.md](api-spec.md) / [requirements.md](requirements.md) / [data-model.md](data-model.md)
> 対象: Go バックエンド（Section 5）。コードは含めない。実装は自分で書く。

## 1. 方針

| 項目 | 内容 |
|------|------|
| テストの層 | ① model（検証ロジック）② store（保存・取得）③ handler（HTTP） |
| 配置 | 各パッケージの `_test.go` |
| 書き方 | 入力と期待値が並ぶものはテーブル駆動、流れを見るものは個別のテスト |
| データ | テストごとに新しい store を作り、テスト同士が影響しない |
| 優先度 | **A** = 必ず書く / **B** = できれば書く / **C** = 余裕があれば |
| 対象外 | 画面（Next.js）のテスト、永続化（F-08）、認証。F-02の「タスクがありません」表示と、F-03の取り消し線はフロントの確認（手動 or 後のE2E） |

要件: F-07 / api-spec POST の検証「前後の空白除去後に1〜100文字」

| ID | 観点 | 入力 | 期待 | 優先度 |
|----|------|------|------|--------|
| M-01 | 通常のタイトル | `牛乳を買う` | OK、同じ文字列が返る | A |
| M-02 | 空文字 | `""` | エラー | A |
| M-03 | 半角空白のみ | `"   "` | エラー | A |
| M-04 | 全角空白のみ | `"　　"` | エラー | B |

| M-06 | 前後に空白 | `"  牛乳  "` | OK、`牛乳` に除去されて返る | A |

| M-08 | 境界: 1文字 | `a` | OK | A |

## 3. store のテスト（保存・取得）

メモリ実装と、Section 6 で作る SQLite 実装の**両方で同じテスト**を使う想定。

| ID | 観点 | 操作 | 期待 | 優先度 |
|----|------|------|------|--------|
| S-01 | 追加→取得 | `Create` → `Get` | 同じ内容。`done=false`、ID が付く | A |
| S-02 | ID の採番 | 2件追加 | ID が重複せず増える | A |
| S-03 | 作成日時と更新日時 | `Create` 直後 | `createdAt` と `updatedAt` が設定されている | B |
| S-04 | 一覧の順序 | 2件を順に追加 | 新しい順（後に追加したものが先頭） | A |
| S-05 | 同時刻の並び | ほぼ同時に2件追加 | ID の大きい順で安定する | B |
| S-06 | 0件の一覧 | 何も追加せず `List` | 空のスライス（`nil` ではない） | A |
| S-07 | フィルタ: active | 未完了1件・完了1件 | 未完了のみ | A |
| S-08 | フィルタ: done | 同上 | 完了のみ | A |
| S-09 | フィルタ: all | 同上 | 2件とも | A |
| S-10 | 部分更新: done のみ | `done` だけ指定 | `title` は変わらない | A |
| S-11 | 部分更新: title のみ | `title` だけ指定 | `done` は変わらない | A |
| S-12 | 部分更新: 両方 | 両方指定 | 両方変わる | B |
| S-13 | `done` を false に戻す | `done=true` → `done=false` | false になる（ゼロ値が「未指定」扱いされない） | A |
| S-14 | 更新日時 | `Update` | `updatedAt` が更新され、`createdAt` は変わらない | B |
| S-15 | 存在しないIDの取得 | `Get(999)` | `ErrNotFound` | A |
| S-16 | 存在しないIDの更新 | `Update(999)` | `ErrNotFound` | A |
| S-17 | 存在しないIDの削除 | `Delete(999)` | `ErrNotFound` | A |
| S-18 | 削除 | `Delete` → `Get` | `ErrNotFound`。一覧からも消える | A |
| S-19 | 削除後の ID | 削除後に追加 | 削除したIDを再利用しない（SQLiteは `AUTOINCREMENT`） | C |
| S-20 | 並行アクセス | 100個のゴルーチンから `Create` | 100件になり、`-race` でエラーなし | A |

## 5. 結合的なシナリオ（handler 経由）

| ID | シナリオ | 期待 | 優先度 |
|----|----------|------|--------|
| F-01〜 | 追加 → 一覧の先頭に出る | 追加したタスクが先頭 | A |
| F-03 | 追加 → 完了 → `status=done` で出る／`status=active` では出ない | フィルタに反映 | A |
| F-04 | 追加 → 編集 → 取得で新タイトル | 反映される | A |
| F-05 | 追加 → 削除 → 一覧から消える | 反映される | A |
| E-01 | 追加 → 完了 → 未完了に戻す | 往復できる | B |

## 7. レビューで決めること（未決事項）

1. **存在しないIDの `DELETE`** は 404 か 204 か（H-73, H-75 の期待値が変わる。api-spec.md の未決事項）
2. **未知のフィールドを拒否するか**（H-23。仕様に書いていないので、拒否するなら api-spec に追記する）
3. **絵文字など結合文字の文字数**（M-14）をどう数えるか（`rune` 単位か、見た目の1文字か）
4. **`done` の指定だけの PATCH でも `updatedAt` を更新するか**（H-54, S-14。現状は更新する想定）
5. カバレッジの目標値（目安: 70〜80%。数値を追うより、優先度 A が全部あるかを重視）

## 8. 進め方

1. このレビューで優先度 **A** を確定する（B、C は余裕に応じて）
2. 書く順番: model → store → handler → 結合
3. バグが見つかったら「再現するテストを先にコミット → 修正をコミット」
4. 完了条件: 優先度 A がすべて実装され、`go test -race ./...` が通る
