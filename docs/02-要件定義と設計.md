# Section 2: 要件定義・設計ドキュメント

## 1. 目的と完成の定義

**目的**: コードを書く前に「何を作るか」「どう作るか」を文章で決める。AIが書いた初稿を自分でレビューし、**差分としてGitに残す**習慣をつける。

**完成の定義**:
- [ ] `requirements.md` `architecture.md` `data-model.md` `api-spec.md` を読み、内容を説明できる
- [ ] `requirements.md` の「未決事項」5つに自分の答えを書いた
- [ ] 各ドキュメントで、AI初稿と自分の修正が**別コミット**になっている
- [ ] `docs/02-design` ブランチを `main` にマージした
- [ ] `learning-log.md` に追記した

## 2. 用語解説

| 用語 | 意味 |
|------|------|
| 要件定義 | 何を作るか（機能・品質）を決める |
| 受け入れ条件 | 「できた」と判断する基準。テストの元になる |
| 機能要件 / 非機能要件 | 動作の内容 / 性能・保守性・セキュリティなど |
| API仕様 | フロントとバックエンドの約束事（URL・JSON形式） |
| ER・データモデル | 保存するデータの項目と関係 |
| ADR | 設計判断とその理由の記録 |

## 3. 手順（コミット単位）

### Step 1: ブランチを切る
```
git switch -c docs/02-design
```

### Step 2: 4つのドキュメントを読む（コードは書かない）
読む順番: `requirements.md` → `architecture.md` → `data-model.md` → `api-spec.md`。
読みながら次をメモする。
- 意味が分からない用語（AIに質問してよい）
- 自分の考えと違う点
- 大きすぎる/小さすぎると感じた点

### Step 3: ドキュメントごとにAI初稿をコミット
```
git add docs/architecture.md
git commit -m "docs: add architecture design (AI draft)"
```
`data-model.md` `api-spec.md` も同様。`requirements.md` は済み。

### Step 4: レビューして修正 → 別コミット
修正方法は2つ。
1. 自分で直接編集する
2. AIに「◯◯を△△に変更して」と依頼する

どちらでも、**コミット前に必ず `git diff` で差分を読む**。
```
git diff docs/architecture.md
git add docs/architecture.md
git commit -m "docs: refine architecture after review"
```

### Step 5: レビュー観点

| 観点 | 問い |
|------|------|
| 整合性 | 要件の機能ID（F-01〜）がすべてAPIにあるか |
| 実現性 | 1〜2週間で作れる量か |
| 一貫性 | 名前（`createdAt` / `created_at`）の規則が揃っているか |
| 抜け漏れ | エラー時の動作は決まっているか |
| 理解 | 自分の言葉で説明できない箇所はないか |

**課題**: `api-spec.md` の「DELETEで存在しないIDは404か204か」を自分で決め、理由を1行書く。

### Step 6: マージ
```
git switch main
git merge docs/02-design
git branch -d docs/02-design
git log --oneline --graph
```

## 4. Git練習ポイント
- `git diff`（作業ツリー）と `git diff --staged` の違い
- `git switch` / `git merge`
- **ファストフォワードマージ**とは何か（`--no-ff` を付けた場合と比較してみる）

## 5. つまずきやすい点
- ドキュメントを一気に直して1コミットにまとめてしまう → ファイル単位、可能なら論点単位で分ける
- AIの出力を読まずにコミットする → レビューが目的なので必ず差分を読む
- 仕様を後から変えたくなる → 変えてよい。**コードより先にドキュメントを直す**のが原則
