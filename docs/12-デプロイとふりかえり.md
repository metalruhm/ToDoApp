**目的**: アプリをインターネットに公開し、README整備とふりかえりで学習を締めくくる。Gitの「やり直し」系コマンド（`revert` `reflog`）も習得する。

**完成の定義**:
- [ ] フロント・APIが公開され、公開URLで登録→ログイン→タスク操作ができる
- [ ] 本番設定（Cookieの `Secure`、許可オリジン、秘密情報）が正しい
- [ ] DBのデータがデプロイし直しても残る（永続化）
- [ ] README に起動方法・構成・スクリーンショットがある
- [ ] `learning-log.md` を読み返して、ふりかえりを書いた

## 2. 公開前の注意（重要）

[requirements.md](requirements.md) の制約にあるとおり、**認証（Section 10）が完成してから公開する**。

公開前チェック:
- [ ] パスワードは平文で保存・出力していない
- [ ] `.env` や秘密情報がGit履歴に入っていない（`git log -p -S"SECRET"` などで確認）
- [ ] 他人のタスクが見えない（Section 10のテストが通る）
- [ ] ログイン試行の回数制限は未実装。**学習用アプリとして個人情報や重要なデータを入れない**
- [ ] 費用がかかるサービスは、無料枠の条件・上限・課金設定を事前に確認する（条件は変わる）

## 3. 用語解説

| 用語 | 意味 |
|------|------|
| デプロイ | アプリを公開環境に配置して動かすこと |
| PaaS | サーバー管理を任せられるクラウド（Vercel / Fly.io / Render など） |
| 環境変数（本番） | 秘密情報や設定を、コードの外からサービスに渡す |
| シークレット | 公開してはいけない設定値（鍵など） |
| リバースプロキシ / rewrites | 受けたリクエストを別のサーバーへ転送する仕組み |
| サイト（site） | Cookieの送信範囲の単位。`vercel.app` と `fly.dev` は**別サイト** |
| `SameSite` | 別サイトからのリクエストにCookieを付けるかの設定 |
| ボリューム | 再デプロイしても消えない保存領域 |
| ロールバック | 前のバージョンに戻すこと |
| `git revert` | 過去のコミットを打ち消す**新しいコミット**を作る |
| `git reflog` | HEADの移動履歴。誤操作の復元に使う |

## 4. 構成の選択

| 案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）** | フロント: Vercel / API: Fly.io（Dockerfileを使用）。フロントの `rewrites` でAPIへ中継 | ブラウザからは**同一オリジン**に見える。CORS・Cookieの問題が出にくい | 設定項目がやや多い |
| B | 同上＋独自ドメインのサブドメイン（`app.` と `api.`） | 分かりやすい | ドメイン取得が必要 |
| C | Render等で両方をDockerでデプロイ | サービスが1つで済む | 無料枠は停止・再起動で遅い場合がある |

**なぜ中継が必要か**: `xxx.vercel.app` から `yyy.fly.dev` へのリクエストは「別サイト」になり、`SameSite=Lax` のCookieが送られず**ログインが保てない**。フロントが `/api/...` で受けてAPIへ転送すれば、ブラウザにとっては同一オリジンになる。

以降は案Aで説明する。

## 6. Git練習：やり直しコマンド

安全に練習するため、**練習用ブランチ**で行う。

### 練習A: `git revert`（公開済みの履歴を安全に取り消す）
- 誤ったコミットを、履歴を書き換えずに打ち消す
- `reset` との違い: `reset` は履歴を巻き戻す（共有済みの履歴には使わない）。`revert` は打ち消すコミットを**追加**する

### 練習B: `git reflog`（消えたコミットの復元）
- 誤って `git reset --hard` して「消えた」コミットを、reflogで見つけて復元する

### 練習C: `git bisect`（発展）
- どのコミットでバグが入ったかを、二分探索で特定する

## 7. つまずきやすい点
- ログインしても直後に未ログインに戻る → Cookieが別サイト扱い。`rewrites` で同一オリジンにする。`COOKIE_SECURE=true` のとき、HTTPSでないと保存されない
- フロントのビルドが失敗 → Vercelの Root Directory が `frontend` か。Nodeのバージョン
- 環境変数を変えたのに反映されない → Vercelは再デプロイが必要。`NEXT_PUBLIC_*` は再ビルドで反映
- Fly.ioでデータが消える → ボリュームのマウント先と `DB_PATH` が一致していない
- 無料枠でAPIが停止する（初回アクセスが遅い）→ サービスの仕様。ヘルスチェックの設定や常時起動の設定を確認
- 秘密情報を誤ってコミット → Section 6の対処を参照。公開済みなら**鍵を無効化して再発行**

<details>
<summary>Step 2 の答え: Next.js の rewrites と API クライアント</summary>

`frontend/next.config.ts`
```ts
import type { NextConfig } from "next";

const apiOrigin = process.env.API_ORIGIN ?? "http://localhost:8080";

const nextConfig: NextConfig = {
  output: "standalone",
  async rewrites() {
    return [
      {
        source: "/api/:path*",
        destination: `${apiOrigin}/:path*`, // /api/todos → {API_ORIGIN}/todos
      },
    ];
  },
};

export default nextConfig;
```

`frontend/.env.example`
```
# ブラウザからは同一オリジンの /api を呼ぶ
NEXT_PUBLIC_API_URL=/api
# Next.jsサーバーが転送する先
API_ORIGIN=http://localhost:8080
```

`frontend/src/lib/api.ts` は変更不要（`BASE_URL` が `/api` になるだけ）。`fetch("/api/todos")` はNext.jsサーバーに届き、APIへ転送される。`Set-Cookie` も転送されるため、Cookieは**フロントのオリジンに保存される**。

ローカルで確認: `frontend/.env.local` に上の2行を書いて `npm run dev` → ブラウザの Network タブで、リクエスト先が `localhost:3000/api/...` になっていること。

Docker Compose側は `build.args.NEXT_PUBLIC_API_URL` を `/api` にし、`frontend` の環境変数 `API_ORIGIN: http://backend:8080` を渡す（コンテナ同士はサービス名で通信できる）。ただし `rewrites` は**ビルド時に評価される**ため、`API_ORIGIN` もビルド引数として渡すのが確実。
</details>

<details>
<summary>Step 3 の答え: backend/fly.toml</summary>

```toml
app = "あなたのアプリ名"          # fly launch で決まる
primary_region = "nrt"            # 東京

[build]
  dockerfile = "Dockerfile"

[env]
  PORT = "8080"
  DB_PATH = "/data/todo.db"
  COOKIE_SECURE = "true"

[mounts]
  source = "data"
  destination = "/data"

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 0

  [[http_service.checks]]
    method = "GET"
    path = "/health"
    interval = "15s"
    timeout = "3s"
    grace_period = "10s"
```
- `[mounts]` … ボリューム `data` を `/data` に付ける。`DB_PATH` と一致させる
- `min_machines_running = 0` … アクセスがないときは停止して節約（初回アクセスは遅い）。常時起動したいなら `1`
- SQLiteなので、`fly scale count 1` で1台に固定する
- 機密性のある値は `[env]` に書かず `fly secrets set` を使う（今回は秘密鍵がない設計）

<details>
<summary>Git練習の答え: revert / reflog / bisect</summary>

**練習A: revert**
```
git switch -c practice/revert
echo "mistake" >> practice.txt
git add practice.txt && git commit -m "feat: add mistake"
git log --oneline -3

git revert HEAD                 # 打ち消すコミットが追加される（エディタでメッセージ確認）
git log --oneline -3            # "Revert ..." が増えている
ls practice.txt                 # 内容が元に戻っている
```
マージコミットを打ち消すときは `git revert -m 1 <ハッシュ>`（親1側＝マージ先を残す）。

**練習B: reflog**
```
git switch -c practice/reflog
echo a > a.txt && git add a.txt && git commit -m "add a"
echo b > b.txt && git add b.txt && git commit -m "add b"

git reset --hard HEAD~1         # 「add b」が消えたように見える
git reflog                      # HEAD の移動履歴。消えたコミットのハッシュが見つかる
# 例: 1a2b3c4 HEAD@{1}: commit: add b
git reset --hard 1a2b3c4        # 復元
git log --oneline               # "add b" が戻っている
```
`reflog` はローカルの履歴で、一定期間後に消える。

**練習C: bisect**
```
git bisect start
git bisect bad                  # 今のコミットは壊れている
git bisect good v0.3.0          # このタグの時点では動いていた
# Gitが中間のコミットに切り替える → テストして結果を伝える
go test ./...                   # backend で実行
git bisect good                 # または git bisect bad
# 繰り返すと「最初に壊れたコミット」が特定される
git bisect reset                # 元のブランチに戻る
```

**後片付け**
```
git switch main
git branch -D practice/revert practice/reflog
```
</details>
